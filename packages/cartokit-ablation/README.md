# `cartokit` Ablation

This package contains the infrastructure to capture the forward evaluation times reported in our PLDI '25 paper, "Fast Direct Manipulation Programming with Patch-Reconciliation Correspondence."

## Purpose

In the paper, we compare our `patch`-`recon` architecture to a more traditional direct manipulation programming architecture, in which a `patch` procedure updates a program that is subsequenttly forward evaluated to produce a new program output. This repository contains the JavaScript programs generated by `cartokit`'s `patch` procedure for all 80 GUI interactions across the six workflows in our benchmark evaluation (Section 6).

## Directory Structure

The table below documents the directory structure and the contents of each directory.

| Directory  | Purpose                                                                                                                                                                                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `data`     | Test datasets used by generated programs.                                                                                                                                                                                                                                          |
| `programs` | JavaScript programs generated by `cartokit`. There are a total of 80 programs, indexed by workflow and interaction. For example, the file `program-4.js` in the `workflow-3` directory represents the program generated as a result of the _fourth_ GUI interaction in Workflow 3. |
| `tests`    | [Playwright](https://playwright.dev/) end-to-end tests that execute each program in the `programs` directory.                                                                                                                                                                      |

## Evaluation

The evaluation in PLDI '25 paper involves instrumenting `cartokit`-generated programs with calls to the browser's [Performance API](https://developer.mozilla.org/en-US/docs/Web/API/Performance) to capture forward evaluation's code execution run time and time-to-quiescent (TTQ) run time. In particular, we use [`performance.mark`](https://developer.mozilla.org/en-US/docs/Web/API/Performance/mark) to define start and end "marks" for measurement and [`performance.measure`](https://developer.mozilla.org/en-US/docs/Web/API/Performance/measure) to capture timings.

For all programs, we measure code execution run time as the time it takes for execution to reach the "bottom" of the program (in the sense of straightline code). Thus, code execution time does not capture the time it takes for _asynchronous_ code (e.g., the callback passed to `map.on('load')`) to finish running. This is where the TTQ measurement comes in! We measure TTQ run time as the time it takes for the map to trigger the `idle` event, signaling that all requested data has fully rendered onscreen. This metric does capture all asynchronous computation.

### Automation

To capture forward evaluation timings for all 80 programs, we created a set of 80 Playwright end-to-end tests, one per program. Each test works by copying the (instrumented) source code from its corresponding program file to `main.js`, which is running on a local development server (http://localhost:5173). The test then triggers a full page reload, which simulates forward evaluating the program to completion. Timing metrics are logged to the console and subsequently captured and persisted to a local file using Playwright's [`waitForEvent`](https://playwright.dev/docs/api/class-page#page-wait-for-event) API.
